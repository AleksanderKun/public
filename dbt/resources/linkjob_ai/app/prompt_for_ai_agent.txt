FAZA 3 — DATABASE

Jeżeli aplikacja posiada bazę danych, wykorzystaj istniejący ORM.

FAZA 4 — BACKEND

Zaimplementuj kompletny backend dla rozmów.

Minimum:

create conversation,

list conversations,

get conversation,

get messages,

rename conversation,

delete conversation,

send message,

generate AI response,

stop generation,

retry,

regenerate,

edit & resend.

Każdy endpoint musi sprawdzać authentication oraz authorization.

Nigdy nie ufaj conversation ID pochodzącemu od klienta.

Użytkownik nie może:

pobrać cudzej rozmowy,

zmodyfikować cudzej rozmowy,

usunąć cudzej rozmowy,

dopisać wiadomości do cudzej rozmowy.

FAZA 5 — AI PROVIDER

Najpierw znajdź istniejącą integrację AI.

Jeżeli projekt posiada abstrakcję providerów — użyj jej.

Jeżeli używany jest Ollama — użyj istniejącej konfiguracji Ollama.

Nie hardcoduj:

API keys,

secrets,

tokens,

private endpoints.

Environment variables muszą być używane zgodnie z istniejącym sposobem konfiguracji projektu.

FAZA 6 — STREAMING

Jeżeli obecna architektura pozwala na streaming, zaimplementuj prawdziwy streaming.

Preferuj istniejący mechanizm.

Jeżeli istnieje SSE — wykorzystaj SSE.

Jeżeli istnieje HTTP streaming — wykorzystaj HTTP streaming.

Jeżeli istnieją WebSockety i są właściwe dla tego przypadku — wykorzystaj je.

Nie dodawaj WebSocketów bez potrzeby.

Streaming musi obsługiwać:

start,

chunks,

completion,

cancellation,

timeout,

provider error,

network interruption.

Nie symuluj streamingu sztucznymi delayami.

FAZA 7 — CONTEXT MANAGEMENT

Zaimplementuj rozsądne zarządzanie kontekstem.

Uwzględnij:

maksymalną długość pojedynczej wiadomości,

token limits,

ewentualne summarization.

Jeżeli rozmowa staje się zbyt długa, ogranicz kontekst w kontrolowany sposób.

Nie dopuszczaj do niekontrolowanego wzrostu promptu.
